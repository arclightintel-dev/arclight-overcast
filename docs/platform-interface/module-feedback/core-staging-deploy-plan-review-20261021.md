**6. `CORE_TRUSTED_PROXY_CIDRS`.** Topology: the ALB is internet-facing (`terraform/modules/alb/main.tf:72–75`), its security group admits only Cloudflare's 15 IPv4 and 7 IPv6 ranges (`terraform/envs/staging/main.tf:46–70` → `alb/main.tf:19, 29`), targets are the task IPs in `10.0.0.0/16` (`variables.tf:18–21`), and `--no-proxy-headers` makes the transport peer the ALB node (a VPC address). Cloudflare sets `X-Forwarded-For` to `[client-supplied entries,] visitor`, and the ALB appends the Cloudflare edge address, so Core sees `…, visitor, cf-edge`. Core walks the chain right to left and returns the first untrusted hop (`arclight_core/services/rate_limit_service.py:81–105`). With **VPC only**, the first untrusted hop is the Cloudflare edge: every visitor behind the same edge POP shares one bucket, and one abusive client can exhaust it for the owner. With **VPC plus Cloudflare ranges**, the first untrusted hop is the visitor address Cloudflare itself appended; client-supplied junk further left is never reached. Internal callers over Cloud Map (Podbay, later NF/SF) arrive with a VPC peer and no header, so they key on their task IP either way.
**Recommendation: VPC plus Cloudflare.** Overcast already maintains the Cloudflare list for the ALB security group, so the value is rendered from the same Terraform locals, `jsonencode(concat([var.vpc_cidr], local.cloudflare_ipv4_cidrs, local.cloudflare_ipv6_cidrs))`, one source of truth; a list update is a normal Overcast change applied to both. Note that staging is not "production" for Core's own check (`rate_limit_service.py:57`: `staging` is excluded), so the required-trusted-proxy guard is not enforced there; the value still matters for keying.

**13. Scale-to-zero mechanism, outage, and the workflow from zero.** Mechanism: `aws ecs update-service --cluster arclight-staging --service arclight-core-staging --desired-count 0` (operator). Two facts the plan does not state. First, reaching zero takes up to **5 minutes**: ECS deregisters the target and waits the target group's deregistration delay, which is the AWS default **300 s** (live attribute; not set in `terraform/modules/alb/main.tf`), before stopping the task. Second, `desired_count` is Terraform-managed and deliberately not in `ignore_changes` (`ecs-service-fargate/main.tf:118–127`), so a `terraform apply` run while scaled to zero would set it back to 1 and start an old-revision task against the migrated database; no apply may run during the window.
**`deploy-service.yml` does not work from zero.** It registers a revision and calls `update-service --force-new-deployment` without `--desired-count` (`deploy-service.yml:129–135`); the service stays at 0, `wait services-stable` returns immediately because 0 running equals 0 desired, and the health check then fails five times against no target. The job goes red and the outage continues until an operator intervenes. Correction: for C4 the operator runs `update-service --task-definition <new revision> --desired-count 1` directly; the workflow is not used for this deploy. Expected outage, end to end: 5 min drain + snapshot (a few minutes) + migration (seconds to a minute) + new task start, 120 s start period, two healthy ALB probes (about 3–4 min): **roughly 12–15 minutes** with everything going right. Cloudflare serves 5xx for the hostname during that window.

**14. Do the health checks read the body?** No. ALB matcher `200`, container check `urlopen` (raises only on non-2xx), workflow `http_code == 200`; evidence in 3. Overcast will add a body check (`.status == "ready"`) to the workflow's verify step as a follow-up, but neither the ALB nor ECS can read a body. **Core should return 503 from `/ready` when `status` is `unavailable`** (`readiness.py:337–345` returns 200 unconditionally). Without that, an unavailable task stays in service at the ALB and is never replaced by ECS. For this deploy the operator verifies `/ready/detail` bodies by hand, as the plan says; that is not a substitute for the status code.

**15. How the redeployed `v2-8c2f8c8` reaches a restored database.** Core connects with `CORE_DATABASE_URL` from `arclight/staging/core/database-url`, whose value embeds the RDS host (`docs/runbooks/restore-rds.md:47–56`; secret version unchanged since 2026-07-01). A snapshot restore creates a new instance with a **new endpoint**. Two ways back: rename the original away and the restored instance to `arclight-staging` (option B; endpoint and all four secrets unchanged), or rewrite the host in the four `database-url` secrets (option A). **Use option B.** Either way `core` and `podbay` need a force-new-deployment to reconnect. With B, the rollback redeploy is `update-service --task-definition arclight-core-staging:7 --desired-count 1` and nothing else changes.

### Corrections to the plan

1. **C4 (blocking)**: replace "`deploy-service.yml` with the new tag; scale back up" with the explicit operator sequence: register the new revision (same fields the workflow uses, plus `CORE_TRUSTED_PROXY_CIDRS`), run the migration task on that revision, then `update-service --task-definition <rev> --desired-count 1`. The workflow cannot start a service from zero (13).
2. **Rollback (blocking, Overcast-owned)**: `docs/runbooks/restore-rds.md` must add `--vpc-security-group-ids <rds sg>` to the restore command and name option B (rename) as the default; Overcast fixes this before C. Also note no manual snapshot exists yet; B3 creates the first.
3. **B2 and D2 execution**: state the mechanism. Preferred: Core ships `preflight` and `broker-bind` commands in the image; fallback: Overcast runs the SQL through a `python -c` override on the Core image. Add the log-stream record to B2's and D2's evidence.
4. **B4**: set `CORE_TRUSTED_PROXY_CIDRS` to VPC plus Cloudflare ranges, rendered from Overcast's existing Cloudflare locals (6). The revision used by the migration task must already carry it.
5. **C1**: add the 5-minute drain (300 s deregistration delay) and the "no `terraform apply` while at zero" rule (13). Optional Overcast change before C: set the Core target group's `deregistration_delay` to 30 s; that is a `terraform/**` change and therefore an owner apply.
6. **C5 / §7 "health checks pass while Core is unavailable"**: the plan assigns Overcast to confirm its health check reads the body; it cannot at the ALB or ECS layer. Core returning 503 on `unavailable` is the fix (14). Overcast adds a body check to the workflow regardless.
7. **D2 restart**: rolling `force-new-deployment` is acceptable; no scale-to-zero. Order: secret, row, restart (8, 10).
8. **D3/D4**: add that the operator must pass Cloudflare Access (OTP) first and that other Entra operators need Access policy changes (9).
9. **E**: the client secrets for `prn_svc_nerfherder` and `prn_svc_sf_seam_smoke` need Secrets Manager shells that do not exist yet (`arclight/staging/nerfherder/core-client-secret`, `arclight/staging/shuttleforge/core-client-secret`); creating shells is a Terraform change and an owner apply (INV-004, DR-1). Not blocking E's registration, blocking NF/SF consumption.
10. **§1 / B5**: Podbay's compatibility with S-033/S-035 is Podbay's to verify; Overcast only confirms the network path and that its own callers are unaffected.

**What Overcast needs from Core that the plan does not provide**: the exact new image tag (`v2-<sha>`) and its ECR digest; a statement that no new required Settings besides `CORE_TRUSTED_PROXY_CIDRS` appear in the Phase 7 build (anything required and absent fails both the migration task and the service at start); the preflight and broker-bind commands, or explicit acceptance of the `python -c` fallback; and the 503 change or an explicit acceptance that readiness is unobservable at the ALB.

**What breaks first in practice**: C4 as written (the workflow leaves the service at zero and the outage runs until someone notices); then a rollback that restores into the default security group; then rate-limit keying on Cloudflare edge addresses if the CIDR list is VPC-only.
